## 1. 제품 목표 및 1.0의 의미

**v1.0 목표:** 사용자가 두 캐릭터의 전투력과 7 Core Stat을 비교하고, 각 평가의 원작 근거·당시 전투 조건·해석·불확실성을 추적하며, 검증된 범위에서 조건부 Matchup을 탐색할 수 있는 **안정적인 근거 기반 분석 웹앱**.

v1.0은 모든 원피스 등장인물의 평가 완료, 작가 공인 전투력, 전체 승률 산출, 또는 모든 Evaluation의 `official` 승격을 의미하지 않는다. E3/미평가 및 해석상 불확실성을 유지하는 것은 실패가 아니라 품질 관리다.

개발 우선순위:
1. **분석 신뢰성:** 원작 Fact / Combat Context / Interpretation / Evaluation / Community Opinion 분리, 출처 정확성, Evidence 연결.
2. **결과 재현성:** 동일 모델·데이터로 동일 결과, 점수·근거 변경 전후 검증, 복원 가능한 기준선.
3. **비교·매치업 완성도:** 7축 비교와 직접 Evidence-aware Matchup의 차이를 유지하고 조건·상성을 설명.
4. **제품 사용성:** 쉬운 탐색·모바일·접근성·일관된 버전 및 출처 표시.
5. **안정적 운영:** 자동 테스트/타입 검사/빌드/Pages 배포, 문서·회귀·권리·성능 점검.

**기존 정상 기능을 다시 만들지 않는다.** 이미 존재하는 캐릭터 검색, 소속 선택, 시점별 Evaluation, 7축 순위, 동축 2인 비교, 전투 타임라인, 출처 링크, Matchup Arena, 패치 내역을 전제로 개선한다.

### v0.3.0 — 출처·근거 신뢰성

- 출처 자료의 **공식 여부**, **원작 직접성**, **보조/팬 해설 성격**을 혼동 없이 표시할 정책을 설계한다. 사이트 도메인만으로 Canon 직접성을 자동 승격하지 않는다.
- 기존 E1/E2/E3의 의미, 1차 원문 미열람, 출처 부족, 불확실성 등을 사실·해석과 분리해 안내한다.
- `SourceCitation`을 재사용하고 출처 레퍼런스/URL·Evidence-전투 연결 검사, 좁은 카드 줄바꿈과 링크 사용성을 검토한다.
- 전체 로스터와 특수 예외(혼합 언어·URL 없음·다중 URL)를 회귀검증한다.
- **승인 지점:** 새 출처 시각 구분 정책이 사용자의 신뢰도 해석에 영향을 줄 경우 표현 방식 결정.

### v0.4.0 — 데이터 무결성·버전 관리

- 실제 과거 스냅샷과 `v0180LegacyCohort.ts` 같은 파생 과거 코호트를 구분한다. 재산정 전에 이전 데이터/결과를 별도 보존하는 최소 방안을 선택한다.
- Character → Battle/Evidence → Evaluation → 계산 모델 → Rank/Matchup 관계를 검사한다.
- 동일 데이터/모델에서 Base·Raw Haki·Final·Overall·대표 Evaluation/시점·순위를 재현한다. 데이터와 계산 모델 버전도 일치시키는 기준을 문서화한다.
- 초기에는 정적 저장소/테스트로 해결하며 DB·관리자 페이지·대규모 리팩터링을 강제하지 않는다.
- **승인 지점:** 기존 저장 구조 변경이나 데이터 마이그레이션 등 중요한 영향이 확인될 때.

### v0.5.0 — 분석의 정밀화

- 전체 현행 Evaluation/7축을 대상으로 스탯 정의, 점수 스케일, E1/E2/E3, Evidence 역할 및 맥락, 공격의 실제 유효타/완력/광역성 구분을 감사한다.
- 고득점 E3, 직접 표본이 제한된 미호크·샹크스 등, 기존 보고서의 스무디/퀸 Speed 사례와 마르코·킹·카타쿠리 등의 Haki/Base 중복 위험을 우선 후보로 검토한다. **검토 후보는 오판 확정이나 점수 변경 명령이 아니다.**
- 승인된 Hybrid Haki 기준을 바탕으로 탁월한 응용/기본 성과/독립적 Raw를 분리한다. 동일 성과를 여러 스탯·Haki 종류에 무비판적으로 중복 부여하지 않는다.
- 개별 항목을 **현상 유지 / 제한적 재산정 제안 / 평가 보류**로 제시하고, 변경 전후 Base/Raw/Final/Overall/순위/15 매치업 영향 및 데이터 버전을 비교한다.
- **승인 지점:** 실제 점수·가중치·평가척도·모델 버전 변경은 사용자 명시적 승인 후 수행한다.

### v0.6.0 — Matchup Arena

- 기존 **15개 직접 대진**의 각 factor, Evidence ID, 전투 조건(참전/상태/목적/환경/제약/외부 개입), 시점 불일치를 재감사한다.
- `attack-access`, `damage-validity`, `defensive-response`, `resource-endurance`, `special-win-condition` 등 기존 Matchup Draft의 정성 factor와 불확실성을 읽기 좋게 연결한다.
- 조건부 시나리오(거리·지형·부상·준비)는 의미 있는 결과 변화와 근거를 설명할 수 있을 때만 별도 설계·승인 후 구현한다.
- 임의 조합에 직접 근거가 없으면 7축/프로필 비교와 Evidence 부족 상태만 표현한다. **Overall 점수 차를 1:1 승률로 환산하거나 +N 고정 상성 보너스를 만들지 않는다.**
- **승인 지점:** 시나리오 컨트롤 범위와 결과 표현 정책.

### v0.7.0 — 사용성·접근성

## 6. 이후 개발의 기본 작업 절차

1. **시작:** `main` 최신 SHA, 릴리즈 버전, `PROJECT_SPEC.md`, 이 로드맵, 관련 실제 코드·데이터와 과거 문서를 확인한다.
2. **기획/영향:** 해당 단계 목표를 기준으로 기존 기능/분석 데이터/계산·출처 연결/모바일/회귀 위험을 확인한다. 중요한 변경은 선택지·전후 영향을 먼저 제시한다.
3. **구현:** 목적에 맞는 최소 단위로 구현한다. 불필요한 리팩터링, 의존성/스키마 교체, 새 서비스 도입은 하지 않는다.
4. **검증:** 변경된 기능 → 경계/오류 → 관련 기존 기능 → 영향에 맞는 전체 회귀. 코드 변경과 검증 완료를 구분한다.
5. **릴리즈:** 작업 브랜치 PR → CI(테스트/TS/빌드) → `main` 병합 → GitHub Pages 배포 확인 → 병합/배포 SHA 및 TEST_REPORT/CHANGELOG/README 갱신.
6. **회고:** 사용자 피드백과 검증 결과를 반영해 다음 단계 우선순위를 조정한다. 단순 표현 패치는 같은 통합 마일스톤에 묶는다.

- 공유 데이터/상태/계산 모델 변경 전 `PatchCheck` 수준 영향 검토, 관련 넓은 변경 후 `RegressionTest`, 정식 릴리즈 전 `ReleaseCheck`를 권장한다. 설치된 전문 Skill이 없으면 프로젝트의 Light Core 절차로 대체한다.
- 기능 구현, GitHub Actions 통과, Pages 배포 성공, 실기기 시각 검증은 **각각 다른 확인 상태**로 보고한다.
- 로드맵은 합의된 기본 방향이지만 변경 가능하다. 세부 목표·우선순위가 달라질 경우 사유와 영향을 PR/문서에 남기며 사용자의 중요한 의사결정을 우회하지 않는다.

## 7. 다음 작업과 로드맵 운영 (v0.3.0 이후)

1. **v0.3.0 실사용 검수:** 브라우저/스마트폰에서 출처 레이블, 카드 상세 펼침, 평가→전투 이동, E등급 도움말, 긴 텍스트 및 중첩 스크롤을 확인한다. 확인 결과에서 발견된 작은 문제는 v0.3.x 안정화 패치로 다룬다.
