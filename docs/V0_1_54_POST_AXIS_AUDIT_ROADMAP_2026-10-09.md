# v0.1.54 이후 개발 로드맵 — 축 검수 종료 이후의 제품 발전 순서

**작성 시점:** 2026-10-09. 이 문서는 실행 우선순위를 제안하는 **개발 로드맵(Proposal)**이다. `PROJECT_SPEC.md` 수정이나 새로운 기획 합의가 아니며, 사용자 승인 없이 평가 정책·핵심 데이터/공식·UI 방향을 바꾸지 않는다.

## 0. 현재 상태와 왜 다음 단계가 필요한가

- v0.1.54: 59개 대표 캐릭터×7축 = **413** Core Final Stat, 62개 Evaluation(과거 포함) / 434 Stat, Haki Raw 합 **244**, Balanced v1.2(7축 동등 가중 / Raw×0.5), 직접 Evidence-aware Matchup **15개**.
- Readiness: E1 30/E2 169/E3 103/**미분류 111**. 이전 148 미분류의 역할 없는 23 + Context-only 14는 개별 분류함. 미분류 111은 **Primary 72 + Secondary 39**로 평가축-Evidence 연결 관계까지 확인됐지만 **평가 등급이 확정됐다는 뜻은 아님**.
- 현재 앱에는 Character/Stat, Evidence, Matchup Arena, Haki 가중 모델, GitHub Pages 자동 검증/배포 및 캐릭터 선택 UI가 이미 있다. **이미 구현된 구조를 다시 만드는 일을 후속 목표로 잡지 않는다.**
- 사최간급 전투력 분석의 목적은 높은 수치 자체가 아니라 **원작 근거 → 조건 → 축 평가 → 계산 → 캐릭터/매치업 표시**의 추적 가능성이다.

## 1. Phase A — 남은 111축 근거 검수 종결 및 데이터 품질 게이트 (최우선)

1. 실제 해당 축을 `primary` 지원하는 **72개**, `secondary` 지원하는 **39개**를 원작 장면, 공식 TV 요약, 기존 `Evidence`의 fact/uncertainty, 합동전·누적 피해·능력 제한과 비교한다.
2. **점수와 readiness를 분리**해 E1/E2/E3 중 하나로 **개별 판정**한다. 직접 근거가 여전히 약한 고점 축은 E3를 유지할 수 있으며, 값 자체를 정보 부족으로 자동 감점하지 않는다.
3. 각 7축이 서로 다른 사건을 같은 가산으로 중복 계산하지 않는지 확인하고, Haki Raw가 이미 Base에 반영된 사건과 중복되는지 조사한다. 시류의 검 무장색 코팅과 같이 원작 패널 확인이 필요한 건 확인 전 확정 금지.
4. 캐릭터별 단위로 판정 이력·검토자·원작 출처·조건·미해결 내용을 축 추적표/문서에 남긴다. 최소 단위 PR, 각 배치의 전후 점수 불변 검증.
5. **완료 게이트:** 413축 readiness 누락 0이 목표일 수 있지만, 출처 부재에 E3를 충분히 표기할 수 있다는 것은 **비교 분석의 불확실성이 해결됐다**는 뜻은 아니다. E3가 많은 고득점 축은 오히려 Phase B의 우선 대상.

## 2. Phase B — 59인 7축 스케일 보정 및 모델 신뢰성 검토 (데이터 검수 종료 후)

1. v0.1.47의 59인×7축 크로스 캘리브레이션, v0.1.49 Overall 민감도·LOAO, v0.1.50·v0.1.51~54의 근거 검수 결과를 함께 대조한다.
2. **중요 후보(예시):** 루치 Combat IQ 68(E3), 퀸 Versatility 80(E2), 죠즈 Defense 84(E2); 마르코/킹/카타쿠리·잭/크래커/비스타 등 비교군의 같은 축과 근거를 나란히 비교한다.
3. 동일한 Haki Raw/Weight 0.5, 7축 합성 규칙을 유지한 채 **점수 변경 전·후** Overall·순위·15 직접 대진의 관련 설명과 상성 표시 변화, 데이터 버전/계산 버전 일치 여부를 비교한다.
4. 개선안은 **A: 현상 유지 / B: 소수 캐릭터·축 재산정 / C: 평가척도 전반 재설계**처럼 **근거·장단점·순위 영향**을 제시하고 **사용자가 최종 선택**한다. C는 구조/정책 변경이므로 ArchitectureReview와 데이터 호환성 검토가 선행돼야 한다.
5. 과거 데이터에 맞춰 보정한 점수로 같은 사건을 평가하면서 '독립 검증'이라 말하지 않는다(데이터 누수). 가능하면 새로운 사건/캐릭터 holdout, 평가자 간 독립 판정으로 비교한다.
6. **완료 게이트:** 59×7 전후 표·Raw/Final 계산 재현성·같은 모델 버전의 결과·기존 Matchup 해석·회귀검증 보고서.

## 3. Phase C — Evidence/점수 해석 UX 마무리 (기존 화면 보존)

- 기존 Character Stats / Evidence 뷰와 Matchup Arena를 **분리 유지**(PROJECT_SPEC §12.1), 현재 B안 캐릭터 선택기와 정보구조를 우선 보존한다.
- 기존 readiness 및 출처 표시가 **사실/조건/해석/점수/커뮤니티** 구분을 충분히 읽히게 하는지 실제 모바일·데스크톱에서 사용자 테스트한다. E3는 '약함'이 아니라 '직접 Evidence 부족'임을 명확히 전달하도록 표시 **안**을 비교한다.
- Evidence 누락/간접성 안내, Chapter/에피소드 링크 가독성, 한 Character의 다른 평가 시점, 레이더/점수의 오해(승률처럼 인식)를 검토.
- 기본 UX 정책을 바꾸거나 새로운 심볼·등급 뱃지·정렬 규칙을 도입하기 전 **현재 UI 스크린샷/피드백 기반으로 사용자 결정**. 단순 버그/접근성/레이아웃 결함은 안전 패치 가능.
- **완료 게이트:** 모바일/데스크톱 주요 흐름 수동 검증, 로드/검색/선택/대진 SWAP·RANDOM·평가시점 변경, Evidence ID와 라벨 일관성.

## 4. Phase D — Matchup Arena 심화 (직접 대진 15개에서 점진 확장)

- 기존 15 대진의 각 요인과 원작 전투 조건(중립/거리/지형/부상/준비/참전/개입)을 먼저 감사. 비교 데이터가 충분할 때만 **Evidence-aware 신규 직접 대진**을 추가.
- SPEC §11/12.1의 후속 후보 중 (a) 거리·지형·부상·준비 등 시나리오 선택, (b) 조건과 출처를 잇는 전투 타임라인, (c) 공유 가능한 Matchup URL/즐겨찾기 등을 **기술적 위험과 사용자 체감 가치**로 나눠 우선순위 제시.
- 실제 대진 근거가 없는 조합은 7축 비교와 Character Profile만 보여주고, **상성 승리·승률·고정 +N 보너스 결론을 생성하지 않는다.**
- **사용자 결정:** 먼저 시나리오 컨트롤을 만들지 / Evidence 타임라인·가독성을 먼저 개선할지. 변경 시 Back/Forward·저장·공유 호환성 사전 검토.

## 5. Phase E — 콘텐츠 확장과 평가 버전 관리

- 추가 캐릭터·해적단은 평가 근거 확보 수준과 사최간급 비교 역할을 기준으로 **제안 → 선택 → Evidence 등록 → 7축 평가 → 교차 비교 → 출시** 순서로 확대. 직책만으로 점수/순위 보너스 금지.
- 미래의 다른 시기/상태(Prime/현재/부상)를 **하나의 캐릭터로 중복 생성하지 않고 Evaluation/Data Version** 구조와 기존 평가 선택 기능을 활용하는 방향 검토.
- SPEC §16의 Draft→Validation→Revision→Publish Admin 에디터는 데이터 규모와 실제 반복 편집 요구가 충분히 커졌을 때 설계한다. 현재부터 백엔드/DB로 무작정 이전하지 않는다.
- 캐릭터 커뮤니티 투표/댓글은 SPEC §17에 따라 **Official Evaluation과 저장·권한·수치 파이프라인을 완전히 분리**해야 하므로 충분한 인증/모더레이션 요구와 사용자 승인 전엔 추가하지 않음.

**비권장:** Readiness를 점수 가산/감점 항으로 만들기, 높은 Overall을 승률로 재해석하기, 미검증 Canon을 자동으로 E1로 승급하기, 각 버전마다 무조건 리팩터링/의존성 교체하기, 핵심 DATA_MODEL/PROJECT_SPEC를 무단 변경하기.

**운영:** 작은 축 판정은 Light Core + 직접 영향 테스트. Raw Haki/계산 공식/공유 데이터 구조를 수정할 때만 PatchCheck·RegressionTest·필요한 아키텍처 검토 강화. 안정판 확정/외부 공개 전 ReleaseCheck, 모바일/브라우저 수동 점검 및 GitHub Pages 커밋 기반 검증. `PROJECT_SPEC.md`의 오래된 v0.1.21 진행 상태 텍스트를 자동 교체하지 않으며 이 문서에서 최신 단계 제안을 독립적으로 관리.
